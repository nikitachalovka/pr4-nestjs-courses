# Звіт до практичної роботи №4

## Тема
Розроблення REST-ендпоінтів засобами NestJS.

## Мета роботи
Опанувати модульну архітектуру NestJS, контролери, маршрутизацію, DTO, сервіси, ін’єкцію залежностей, HTTP-статуси та обробку виключень; реалізувати REST API з CRUD-операціями.

## Індивідуальний варіант
**Варіант 9 — онлайн-курси та підписки.**  
Маршрут ресурсу: `/courses`.  
Поля: `title`, `price`, `durationHours`, `difficultyLevel`, `instructor`.

## Хід роботи
1. Підготовлено структуру застосунку NestJS з кореневим `AppModule`.
2. Створено `CoursesModule`, який реєструє контролер і сервіс.
3. Описано тип сутності `Course`, DTO створення `CreateCourseDto` та DTO оновлення `UpdateCourseDto`.
4. Реалізовано `CoursesService` з трьома початковими записами в in-memory сховищі.
5. Реалізовано контролер із маршрутами:
   - `GET /courses` — список, пошук за `search` і обмеження `limit`;
   - `GET /courses/:id` — отримання одного курсу;
   - `POST /courses` — створення;
   - `PATCH /courses/:id` — часткове оновлення;
   - `DELETE /courses/:id` — видалення.
6. Налаштовано статуси 201 Created і 204 No Content, а також 404 Not Found для відсутнього запису.
7. Додано заголовки `X-API-Version` і `X-Service-Status` до відповіді списку.
8. Додано валідацію вхідних DTO та файл `requests.http` зі сценаріями перевірки.

## Результати тестування
Перелік запитів і очікуваних HTTP-статусів наведено в `README.md` та `requests.http`. Фактичне тестування виконується локально командою `npm run start:dev`. Після виконання запитів необхідно вставити власні скриншоти запуску сервера та відповідей API в цей звіт або README.

## Відповіді на контрольні питання

### 1. Що таке IoC та як DI реалізований у NestJS?
Inversion of Control — принцип, за якого створення об’єктів і керування їхніми залежностями передається контейнеру фреймворку. У NestJS класи-провайдери реєструються в модулі, а контейнер створює їх і передає залежності через конструктор. У роботі `CoursesService` впроваджується в `CoursesController` через constructor injection.

### 2. Різниця між модулем, контролером і провайдером?
`@Module()` групує компоненти та описує імпорти, контролери й провайдери. `@Controller()` приймає HTTP-запити та визначає маршрути. `@Injectable()` позначає клас як провайдер, у якому розміщується бізнес-логіка; наприклад, `CoursesService`.

### 3. Чому DTO створюють класами, а не інтерфейсами?
Класи зберігаються в JavaScript після компіляції та доступні під час виконання. Це дає змогу використовувати метадані й виконувати runtime-валідацію. TypeScript-інтерфейси зникають після компіляції.

### 4. Які декоратори витягують параметри запиту?
`@Param('id')` отримує параметр маршруту, наприклад `/courses/1`; `@Query('search')` отримує параметр рядка запиту, наприклад `?search=web`; `@Body()` отримує тіло запиту; `@Headers('назва')` читає заголовок запиту. У цій роботі застосовано `@Param`, `@Query` і `@Body`.

### 5. Які статуси повертаються за замовчуванням для GET, POST і DELETE? Як їх змінити?
За замовчуванням NestJS повертає 200 для GET і DELETE та 201 для POST. Статус можна явно встановити декоратором `@HttpCode()`, наприклад `@HttpCode(HttpStatus.NO_CONTENT)` для DELETE. У цій роботі POST має 201, DELETE — 204.

### 6. Як працює обробка виключень NestJS?
Вбудований exception layer перехоплює HTTP-виключення та формує HTTP-відповідь. `throw new NotFoundException()` повертає статус 404 і JSON із повідомленням, назвою помилки та `statusCode`. У сервісі так обробляється запит неіснуючого курсу.

### 7. Як додати кастомний HTTP-заголовок?
Декоратор `@Header('назва', 'значення')` задає заголовок відповіді методу контролера. У роботі для `GET /courses` встановлено `X-API-Version: 1.0` та `X-Service-Status: operational`.

### 8. Чим відрізняються PUT і PATCH?
PUT зазвичай замінює весь ресурс переданим представленням, тоді як PATCH застосовує часткові зміни лише до переданих полів. У цій роботі використано PATCH, щоб оновлювати окремі поля курсу.

## Висновок
У межах практичної роботи підготовлено REST API для керування онлайн-курсами засобами NestJS. Реалізовано CRUD-маршрути, DTO, сервіс із in-memory сховищем, ін’єкцію залежностей, пошук і обмеження результатів, кастомні HTTP-заголовки, статуси відповідей та обробку 404. Для перевірки підготовлено набір HTTP-запитів. Перед здачею потрібно запустити проєкт, виконати запити, додати фактичні скриншоти та опублікувати код у власному GitHub-репозиторії.
